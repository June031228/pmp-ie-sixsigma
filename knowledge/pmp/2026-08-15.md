# PMP · 第 3 课：范围管理（需求收集 / WBS）（第 1 轮）

> **承接第 2 课** —— 第 2 课我们用《项目章程》把"立项"正式授权，并据此制定《项目管理计划》，章程里锁定的是"高层级需求"与"概括预算"。那么，**这些高层级需求如何变成团队能执行、能估算、能验收的具体工作？谁来决定"做什么、不做什么"？** 这就是本课「范围管理（Scope Management）」，它把模糊的目标，钉成清晰的边界。

## 一、导语
第 2 课的智能报销 App，章程里只写了"拍照识票、审批流、ERP 对接"三句话。真要开工，这三句话远远不够：拍照识票要不要支持增值税发票？审批流是固定三级还是可配置？ERP 对接哪些模块？范围管理就是要回答这些问题，并用 WBS 把工作拆到"看得见、估得准、交得出"的颗粒度，同时挡住无休止的范围蔓延。

## 二、核心知识点

### 1. 范围管理在管什么
范围 = 为交付产品 / 服务所必须做的全部工作，以及为此被明确排除的工作。两大产出：
- **项目范围说明书（Scope Statement）**：详细描述可交付成果、验收标准、除外责任（"不做什么"同样重要）。
- **范围基准（Scope Baseline）** = 范围说明书 + WBS + WBS 词典，是后续进度、成本、质量估算的共同地基。

### 2. 需求收集（Collect Requirements）
把干系人"想要的"变成"写下来的"。常用技术：
- 访谈、焦点小组、引导式研讨会（如 JAD）；
- 问卷与标杆对照；
- 观察（Shadowing）、原型法（Prototype）——对界面类项目尤其有效。
产出：**需求文件**与**需求跟踪矩阵（RTM）**，从需求追溯到可交付成果，防遗漏。

### 3. WBS（工作分解结构）—— 范围的"骨架"
- 定义：以**可交付成果**为导向，把项目逐层分解为**工作包（Work Package）**的层级树。
- **100% 规则**：WBS 包含且只包含全部项目工作——既不漏项，也不多塞。
- 颗粒度：一般 3–5 层；工作包控制在 **8–80 小时**或 **2–4 周**内可完成、可估算、可指派。
- 控制账户（Control Account）：WBS 上用于挣值管理的管理节点。

### 4. WBS 词典（WBS Dictionary）
对每个工作包的文字说明：内容、交付物、工期、成本、负责人、验收标准。与 WBS 配套，避免"名字看懂了、细节一团雾"。

## 三、真实案例：电商网站 WBS 拆解

**背景**：承接前两课，某零售企业自建电商网站，章程锁定——预算 ¥120 万、工期 5 个月（2026-07 至 2026-11）、sponsor 为 CTO。高层级范围：商品、交易、用户、支付、运营五大域。

**WBS 第一层（5 大域）→ 第二层（示例：交易域）**：
- 1.0 商品管理：1.1 商品录入、1.2 库存同步、1.3 分类与搜索
- 2.0 交易订单：2.1 购物车、2.2 下单与改单、2.3 订单状态机、2.4 售后退款
- 3.0 用户中心：3.1 注册登录、3.2 地址管理、3.3 会员体系
- 4.0 支付对接：4.1 微信支付、4.2 支付宝、4.3 对账
- 5.0 后台运营：5.1 数据看板、5.2 营销活动

**工作包示例（2.2 下单与改单）WBS 词典**：
| 字段 | 内容 |
|---|---|
| 交付物 | 下单 API + 改单 API + 幂等控制 |
| 工期 | 8 人日 |
| 成本 | ¥3.2 万（2 名开发） |
| 验收 | 并发 500 QPS 下下单成功率 ≥ 99.9% |

**范围蔓延拦截**：第 6 周业务方提出"加直播带货模块"。PM 依据 WBS 词典判定其为范围外，走变更控制（CCB），评估需 +¥18 万 / +3 周，经批准才纳入 6.0 新增域——把"拍脑袋加需求"变成"可决策的变更"。

**结论**：WBS 让"三句话范围"变成 30 个可估算工作包；100% 规则 + 变更控制，是范围不失控的两道闸门。

## 四、与前后知识的联系
- **向后（第 4 课·进度管理）**：WBS 的工作包将拆成**活动**并排定依赖、算出关键路径——没有 WBS，进度计划就是空中楼阁。
- **向前（第 2 课）**：范围说明书源自章程的"高层级需求"，是整合管理计划在"范围"这一维的落地。

## 五、小结与延伸
- **一句话**：范围管理 = 用 WBS 把目标拆到底、用 100% 规则和变更控制挡住蔓延。
- **延伸**：PMBOK® Guide 第 5 章「范围管理」；推荐对比 Agile 下"范围可变、时间 / 成本固定"的差异。
